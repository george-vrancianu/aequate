# Open math recognizers for the browser default

Research for [#4](https://github.com/george-vrancianu/aequate/issues/4) (part of #1). Question: which open models can be the default in-browser handwriting-to-LaTeX recognizer, and is any stroke-based (online) model usable off the shelf? Context: `docs/handoff.md` section 5.

Researched 2026-10-08 against repos, model cards, and papers. Every figure below is linked to its source. Statements marked *(assessment)* are my own judgement, not a sourced fact.

## Terms

- **Online / stroke-based**: the input is the pen trajectory (a sequence of points per stroke, e.g. InkML).
- **Offline / image-based**: the input is a raster image. Strokes can always be rasterized, so an image model can serve a stroke-capturing board.
- **ExpRate**: the share of whole expressions recognized exactly, which is the CROHME headline metric.

Most current "HMER" papers that report CROHME numbers (BTTR, CoMER, PosFormer, TAMER) are **image-based**. They train and test on CROHME inks rendered to images. For example, CoMER says it generates LaTeX "from a handwritten mathematical expression image" ([CoMER paper](https://ar5iv.labs.arxiv.org/html/2207.04410)). Very few open models take strokes.

| **TAMER** (AAAI 2025) | **None** (no LICENSE file; [repo](https://github.com/qingzhenduyu/TAMER)) | 61.23 / 60.26 / 61.97 ([README](https://github.com/qingzhenduyu/TAMER)) | 99.9 MB `.ckpt` for CROHME, plus HME100K checkpoints ([repo](https://github.com/qingzhenduyu/TAMER)) | None published |

All four are trained on the CROHME training set, with HME100K as an extra option for TAMER. They are PyTorch Lightning code with a DenseNet encoder and a beam-searched transformer decoder. Exporting to ONNX is feasible: the encoder exports directly, and the decoder needs a per-step export with the beam search done in JS. CoMER's attention-refinement module adds work *(assessment)*. Only BTTR has a license that permits redistribution.

## 4. Fine-tuning effort

- **"Fine-tune a CROHME stroke model" is really "train a stroke model".** There is no open, licensed stroke model to fine-tune. TAP has no license and runs on Theano. Seshat is a GPL grammar system, not a network you fine-tune. MathWriting's model is unreleased. The most credible recipe is MathWriting's: an encoder-only CTC Transformer, 35M params, trained from scratch on ink ([arXiv 2404.10690](https://arxiv.org/html/2404.10690v1)). This recipe is moderate work: a data pipeline from InkML, ink augmentation, and GPU-days of training *(assessment)*. **Data licensing is the main blocker.** MathWriting is CC BY-NC-SA 4.0 ([repo](https://github.com/google-research/google-research/tree/master/mathwriting)). Whether weights trained on it inherit NC terms is legally unsettled, and Aequate needs a lawyer's view before shipping such weights. The CROHME data is far smaller: CROHME23 has 17k human-written inks vs MathWriting's 253k ([arXiv 2404.10690](https://arxiv.org/html/2404.10690v1)).
- **Image HMER models (BTTR/CoMER/TAMER)**: the repos include full training scripts (TAMER trains with 4 GPUs via DDP; [README](https://github.com/qingzhenduyu/TAMER)). Fine-tuning on extra data is routine. Only BTTR's license allows Aequate to use it.
- **Distilling TexTeller**: Apache-2.0 weights and dataset permit distillation. The teacher is about 300M params. A student around Pix2Text-MFR size (about 120 MB fp32) is plausible. Before claiming clean provenance, the handwritten subsets' upstream licenses need checking *(assessment)*.
- **Pix2Text MFR**: a standard HF `VisionEncoderDecoder` (TrOCR). It can be fine-tuned with stock `transformers` tooling, and re-exported with `optimum` exactly as upstream does ([model card](https://huggingface.co/breezedeus/pix2text-mfr-1.5)).

PaddleOCR wins for handwriting, and its license is the same as Tesseract's. Its official browser SDK removes Tesseract's one remaining advantage, ease of use.

## Answer

**No open stroke-based math recognizer is usable off the shelf in a browser.** The only stroke models with public weights are TAP and Seshat. TAP has no license, runs on Theano, and dates from 2019. Seshat is GPL-3.0 C++ at roughly the 37% CROHME-2014 level. Google's MathWriting ink model (35M params, the strongest published stroke result) has no released weights, and its training data is CC BY-NC-SA. The CROHME leaderboard models with weights (CoMER, PosFormer, TAMER) are image-based, and all but BTTR (MIT) lack a usable license. The realistic browser default today is image-based: rasterize the strokes on pen-up and run **Pix2Text MFR 1.5** (MIT, official ONNX, about 120 MB fp32). The second choice is **BTTR** (MIT, about 54% CROHME ExpRate, needs ONNX export work). **TexTeller** (Apache-2.0, official ONNX but about 1.25 GB) belongs on the GPU server. Its public weights were trained on the CROHME test sets, so no honest CROHME figure exists for it. For the text layer, use **PaddleOCR**: it is Apache-2.0 like Tesseract, has far better handwriting accuracy, and has an official browser SDK. Tesseract's own FAQ says it is not for handwriting.

## Recommendation for the recognition spike

1. **Browser default for the spike:** rasterize strokes, run Pix2Text MFR 1.5 ONNX in `onnxruntime-web`, and try int8 quantization. Measure pen-up-to-LaTeX latency on the student tablet target and the download size.
2. **Measure accuracy on held-out data yourself.** Use the CROHME 2019 test set and the MathWriting test split, evaluation-only and internal. Run the same harness on Pix2Text MFR, BTTR, and TexTeller (server). No vendor-published CROHME number exists for the image-to-LaTeX family, and TexTeller's public weights are contaminated with the test sets.
3. **Reframe the decision in #1.** "Fine-tune a CROHME model" is not available as stated, because no licensed stroke model exists to fine-tune. The real choice is:
   - (a) **Train a stroke model** using the MathWriting CTC Transformer recipe. This is the best accuracy-per-parameter evidence, but it is blocked on the CC BY-NC-SA data question.
   - (b) **Distill TexTeller** (Apache-2.0) into a Pix2Text-sized image student. This has a cleaner license, but the provenance of its handwritten subsets still needs checking.

   Make the decision after step 2 shows how far the off-the-shelf Pix2Text MFR is from good enough.
4. **Keep the adapter stroke-first.** Store and pass strokes, and rasterize inside the image adapter. A later stroke model can then replace it without changing the protocol.
5. **Use PaddleOCR (PaddleOCR.js) for the text layer.** Drop Tesseract from the plan.
6. **Get a legal opinion** on whether weights trained on CC BY-NC-SA data (MathWriting) may ship in an AGPL/MIT product. This also covers TexTeller's handwritten subsets, if their sources turn out to include MathWriting.
