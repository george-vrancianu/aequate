## 5. Analysis (hand-written; facts first, recommendations labelled)

### 5.1 Facts from the run

- Set: 86 hand-labelled steps (more than the ~30 asked for: 54 written first, 8 stress steps added after the first clean run, D63-D65 after a stress probe, D66-D71 added AFTER review round 1 from the reviewer's failing probes, and D72-D86 added AFTER review round 2 to probe the family behind blocking finding B1'), 56 labelled changed, 30 labelled same. Result: 46 changed steps flagged and named correctly, 0 misnamed, 0 changed steps called SAME (FN), 25 same steps called SAME (TN), 0 same steps flagged (FP), 15 UNDECIDED (10 labelled changed, 5 labelled same: D54, D61, D64, D65 and D72-D78, D80, D81, D85, D86). No timeouts. Precision 100% (46/46); recall 82% with undecided counted as a miss (46/56), 100% over decided steps. Split by tier: D1-D71 (the round-1 set) 43 TP / 24 TN / 4 UNDECIDED as before; D72-D86 (post round 2) 3 TP, 1 TN, 11 UNDECIDED. The drop in recall is the price of the B1' fix: the 11 new undecided are all steps whose constraints contain `x^(2/3)`, `x^(4/3)` with an inequality, on which `solveset` is not trusted (see the SymPy defect bullet below). The first version of this prototype (commit bb8505c) scored 65 steps at 100% / 98% but had three defects found by the reviewer; D66-D71 and D72-D86 are probes written from those failures and from the reviewed family, therefore regression cases, not an independent sample. Timing is in section 3 (it varies per run).
- The 20 original steps: S7 (unchanged) 17 correct / 2 partial / 0 wrong / 1 undecided; S7b 18 / 2 / 0 / 0. The only difference is #13 (`y=2x+3` -> `x=(y-3)/2`, two variables), which S7 left undecided and S7b settles as EQ. The 2 partial are the one-way steps #14, #15, which both strategies reject as plain NEQ at the numeric stage, exactly as before. The three domain traps (#7, #17, #19) are flagged with the same named values as S7 (`x = 1`, `x = 1`, `x = pi/2 + k*pi`).
- Domain representation: a conjunction of atomic constraints (`e != 0`, `e >= 0`, `e > 0`) per side, solved per variable where possible, not a set over R^n. Reasons: (1) SymPy has no usable R^n set type for this: `ProductSet` only expresses separable domains, and a constraint like `x*y >= 0` or `x != y` is not a product (the first version of this question, `sqrt(x)*sqrt(y) -> sqrt(x*y)`, needs exactly such a constraint); (2) the constraints themselves are what an amber message needs ("only if x - y != 0"), and the run prints them when the step changes them (column "constraint diff"); (3) comparing two conjunctions splits cleanly into an exact part (one-variable atoms, solved into intervals plus excluded points) and an opaque part (compared by canonical key), and anything that falls between is refuted by a point or reported as undecided. Cost: sameness of two different-looking opaque constraints cannot be proved (D54, D65), and the exact set of a multi-variable change is not computed, only a witness point plus the changed constraints.
- Canonical comparison of `ImageSet`s and unions: periodic exclusion sets are decoded to classes `{(q + c*k)*pi + rest}` and reduced to the minimal period, so equal sets written differently compare equal and differences are named. Evidence: D10 (`1+cos(2x)=0` vs `cos(x)=0`), D57 (`tan x + cot x` vs `1/(sin x cos x)`: union of two sets vs sets from a product), D59 (half-angle: `sin(x/2)=0` U `cos(x/2)=0` equals `sin x=0`), D9 / D58 (`x = k*pi/2` as one class vs union of two ImageSets), D11 (named difference `pi/2 + k*pi` out of a union of three classes). All SAME where equal, none false-flagged. This is the failure the CAS spike warned about (equal sets written as different ImageSets flagged as "domain changed"); it did not occur on any step here.
- SymPy defect found and guarded: `solveset(sin(x) > 0, x, Reals)` returns `Interval.open(0, pi)` (one period, not the whole solution set). Inequalities containing sin/cos/tan/cot/sec/csc are therefore never solved; they stay opaque (D51, D52, D53, D63, D54, D65). Equations (`!= 0` atoms) with trig return complete ImageSets and are used.
- A bug found by a stress probe, fixed, kept as D63: when an opaque constraint is present (here `sin x >= 0`), the per-variable exclusion set of a `!= 0` atom (`cos x != 0`, i.e. `pi/2 + k*pi`) is only a superset of the true difference (3*pi/2 + 2k*pi is already outside `sin x >= 0`). S7b now names such a step by a witness point only and treats the per-variable sets as hints.
- The pointwise check is a second line of defence in both directions: it can only prove CHANGED (a differing exact point is a proof), and a symbolic difference that no point confirms is reported UNDECIDED. In this run it never contradicted the symbolic result.
- Multi-variable results are named by one exact witness point (plus, for opaque atoms, the constraints only before / only after). The check "named correctly" for those steps compares the witness against a label predicate I wrote, so it verifies one point in the region, not the whole region.
- Real-power convention (stated in `domain.py`): odd roots are real (x^(2/3) and `(x^(1/3))^2` are defined on all R), x^0 needs x != 0, `x^y` with symbolic y, `log` with a base and unlisted functions are UNDECIDED. D30, D31, D34 and D66-D69 depend on the odd-root convention; with SymPy's principal branch they would get different answers. The first version applied the convention only when collecting constraints, while `solveset` and the pointwise refuter used SymPy's mixed branches: `solveset(x**(1/3)+3 >= 0)` returned the FiniteSet {-27}, `solveset(x**(2/3) > 0)` the principal-branch (0, oo), and `(-2)**(1/3)` counted as undefined. That gave a false SAME on `ln(x^(2/3)) -> (2/3) ln x`, false amber on `1/cbrt(x) -> x^(-1/3)` and a wrong named set on `sqrt(x^(1/3)+3)^2`. Fix: every constraint expression is rewritten, before normalising, solving and evaluating, to the real-root form `(sign(b)*Abs(b)**(1/q))**p` for `b**(p/q)` with q odd, so all three parts follow one convention (D66-D69 now correct). Decimal exponents are their Rational value (`x^{0,5}` = x^(1/2), `x^{2.0}` = x^2); the first version treated a Float exponent as irrational (base > 0) and flagged D70/D71-type steps falsely. Only a genuinely irrational constant exponent needs base > 0.
- Defect signal: when the symbolic comparison says SAME but a grid point disagrees, the verdict is now UNDECIDED (logged in the `why` column), not CHANGED: the refuter and the solver use separate evaluation code, so a conflict means a bug in one of them. It did not occur in this run.
- Undecided cases of the round-1 set (4 of 71): D54 and D65 (different but equivalent trig inequalities, opaque keys differ), D61 (the difference lies on the plane `x - y = 10`, no grid point is on it; the constraint `x - y - 10 != 0` is still reported as the assumption), D64 (`log_2`, unsupported). None was turned into a false SAME or a false CHANGED. The 11 further undecided steps D72-D78, D80, D81, D85, D86 are the solver guard firing (next bullet); none was a false SAME or false CHANGED either, and the 4 decided ones in the family (D79, D82, D83, D84) are correct.
- SymPy defect found in review round 2 (B1') and guarded: `solveset` is WRONG on `Abs(x)**(p/q)` with q odd and p even, the exact form the real-root rewrite produces: `solveset(Abs(x)**(2/3) - 1 >= 0, x, Reals)` = EmptySet (truth |x| >= 1), `solveset(4 - Abs(x)**(2/3) >= 0, ...)` = all of R (truth [-8, 8]); the same with `(x**2)**(1/3)`, so a different rewrite would not avoid it. Before the guard, `sqrt(4 - x^(2/3))^2 -> 4 - x^(2/3)` was a FALSE SAME (green), and `ln(x^(2/3)-1) -> ln(x^(1/3)-1)+ln(x^(1/3)+1)` was named in the wrong direction. Fix: whenever an atom contains Abs, sign or a non-integer power, the solveset result (inequality or `!= 0` solution set) is cross-checked by exact evaluation of the atom at about 30 fixed probe points (small and large rationals up to 10^4) plus points around and between every returned endpoint) and, on any disagreement, the step is UNDECIDED ("solver not trusted"). Far points (+/-10 .. +/-1000) were also added to the refuter grid. A conflict between a named set and the witness is not separately handled (not added; the guard made it unnecessary for this family). Cost: those forms become undecided instead of decided (D74-D78, D85, D86 would otherwise be named); a substitution fallback (solve in `t = cbrt(x)`) would recover them and is not built. Limits of the guard: it is a sampler, not a proof; it only catches errors that a probe point or an interval end exposes; a solver error confined to a gap between probe points and endpoints would pass.
- Label sanity: every label was also checked by evaluating before and after at exact points where both sides are defined (column "numeric check of label"): all agreed. One label was wrong before this check: `|x|/x -> 1` (invalid, -1 for x<0) was replaced by `|x|/|x| -> 1` (D55).

### 5.2 Limits of this evidence

- The labels, the rules and the stress steps were written by the same agent; the stress tier was added after seeing a clean first run, and the D63 bug came from that probing. 0 FP / 0 FN is therefore evidence on 86 chosen steps, not an error rate. A different author would probably find more undecided and some wrong ones.
- Rule coverage is exactly the whitelist: Add, Mul, Pow (rational exponents, integer exponents), exp, log (natural), sin, cos, tan, cot, sec, csc, asin, acos, atan, Abs, sinh, cosh, tanh, constants. Everything else (asec/acsc/acot, floor, factorials, Piecewise, symbolic exponents, complex numbers) is UNDECIDED by design.
- Equations: both sides are treated as one domain; only two equation steps of the original 20 exercise this. Systems and inequalities as steps are not covered.
- The grid has at most 40 / 11 / 6 values per variable for 1 / 2 / 3 variables and a 1500 point budget; it is a refuter, not a proof of sameness. Sameness rests on the symbolic comparison (equal one-variable sets and equal opaque keys), which relies on SymPy's `solveset` for polynomial, root and log atoms being correct. No independent check of `solveset` beyond the grid exists, and `solveset` has now been caught being wrong on this input class twice (`solveset(x**(1/3)+3 >= 0, x, Reals)` = {-27} in round 1, bypassed by the real-root rewrite; `Abs(x)**(2/3)` forms in round 2, which the rewrite itself creates; both found by the reviewer, neither fixed in SymPy). The round-2 guard now samples the solver on Abs/sign/non-integer-power atoms; other atom kinds (plain polynomials, logs) are still trusted without a check. Rational exponents with an odd denominator and decimal exponents appear in only D30-D34 and D66-D86 of the labelled set, and D66-D86 were written from the reviewer's failures or the family around them. Not covered: the x1-x7 extra trig identity checks of the original harness were not run through S7b. The `Dset` per-variable report for several variables with only one-variable atoms is a disjunction (the output now says OR), not a conjunction.
- Parse guards are untouched and reject some natural inputs (`x(x+1)` implicit call syntax: D6 and D22 were first rejected as "undeclared function x" and rewritten with `\cdot`).
- Timing: all steps are small; nothing here stresses the 2 s timeout. The slowest are trig steps with several constraints (see section 3). Deeper nesting or three or more variables with trig would grow the solver and grid cost; not measured.

### 5.3 Recommendations (not facts)

- Is S7b reliable enough to drive an amber "only if x != a" verdict? Yes for the shape it covers (whitelisted rules, real-root convention for odd denominators, decimal exponents read as their rational value), with these limits: (0) steps with odd-root powers (x^(p/q), q odd) inside an inequality or `!= 0` constraint may be shown green from a SAME only after the guard passed; in practice most of them come back UNDECIDED ("can't check"), so do not promise to decide them; (1) only when the verdict is CHANGED from the whitelist rules above; any UNDECIDED, unsupported node or timeout must show as "can't check", never green; (2) for one variable with solved sets, the named set (finite points, intervals, periodic classes) is exact as far as `solveset` is right (it was wrong twice on odd-root forms, see 5.1/5.2; those forms are now sample-checked and become UNDECIDED when the solver disagrees with exact evaluation; other kinds of atoms are not cross-checked) and can be shown as "only if x != 1" or "only if x is not pi/2 + k*pi"; (3) for several variables, or with trig inequalities, show the assumption as the constraint list ("only if x - y != 0"; the list now diffs all normalised constraints, not only the opaque ones), not as a computed region: the exact region is not computed and the witness is a single point; (4) a SAME verdict should be shown green only together with the numeric/solution-set verdict, and "SAME domain" with opaque trig inequalities is only as strong as the key match (it proves nothing when the keys differ: that is UNDECIDED, which is the safe side).
- Treat the amber text as an assumption to be checked by the student, not a proof that the step is correct elsewhere; S7b says nothing about whether the rewrite is valid (it runs after the numeric check, as S7 did).
- If a decision needs more than this: a second author for the label set, a larger multi-variable set with trig, and an independent `solveset` cross-check for ALL atoms (the guard here covers only Abs/sign/non-integer-power atoms, by sampling; interval arithmetic over the claimed difference would be stronger) before relying on SAME, and a substitution fallback for odd-root forms.
- Policy questions for "Decide CAS equivalence semantics": the odd-root convention (real vs principal) changes verdicts on rational-exponent steps; `x^y` with symbolic y is undecided and may need a positive-base assumption; whether `sqrt(x)*sqrt(y) -> sqrt(x*y)`-type steps (valid for positive values, domain-enlarging otherwise) show amber with "only if x >= 0 and y >= 0".
